## Fixes in Preview 23 (based on prompt 22 and four screenshots)
1. **Content Studio / website pending:** A scheduled package can reuse an already-ready Content Package/CMS article and comment for the same clip even when one entry stores an absolute path and another a basename. An existing article URL is consumed instead of re-publishing it. On CMS failure, package error and website failure are reflected in linked scheduled posts rather than silently remaining at `pending_generation` / “chờ tạo web”. A failed/retryable package can be put back in the content worker queue; the request does not run CMS/LLM synchronously.
2. **Content UI / comment:** Added failed-only filter, per-package retry action and visible busy/success/error feedback for field regeneration. Missing CMS URL blocks comment regeneration with an explanation; Content Studio shows CMS error and `no_llm_error_fallback` reason. A title retry does not falsely clear an unrelated website failure. No First Comment is claimed ready without an article URL.
3. **Page–Token allocation:** Removed UI's undefined `targetPages` reference in group allocation. Allocation is computed server-side from active, fingerprint-matching, verified Page–Token bindings. If any Page is unmapped, API returns blocked Page ids and makes **no partial assignments**. It does not assign a random token by list position. Existing token group selection and Page snapshot still apply.
4. **Meta direct publishing / immediate action:** `/api/publish/reel` now uses the exact Page–Token preflight used by scheduling, rather than trusting a cached Page token. It records success only when Meta returns an object id. Init/finish non-JSON/error responses are handled; finish uncertainty is marked `outcome_unknown`. Comment failure after a successful Reel does not turn it into a failed Reel that could be re-published.
5. **Scheduler / uncertain outcomes:** A worker exception or ambiguous response after publish starts becomes failed/non-auto-retryable and requires reconciliation; a stale `publishing` claim after `publish_started_at` continues to fail closed. Legacy queue records with a persisted Page token but no `token_id` remain compatible, while new records with `token_id` still require current verified mapping.
