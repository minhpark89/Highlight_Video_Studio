# v1.3.2 Jobs, render preferences, responsiveness and desktop icon

The implementation addresses the reported globe icon, a Jobs history with 1,264
rows, a manual four-render selection reverting to two, and slow app responses.

## Changes

- The packaged icon is served locally as favicon. The Windows launcher assigns
  the application icon to its own form and periodically updates both native
  icon sizes on the Chrome app window. The normal Chrome profile is retained.
- Jobs has filters for error, queued, running and completed, live totals,
  search, 25/50/100 rows per page, previous/next controls and a bounded scroll
  area. Full IDs and error details make similar jobs distinguishable.
- The list API sends summaries without nested transcripts or clip metadata.
  Job details still expose the full selected record; the legacy list API
  remains available. Queue polling and the worker avoid copying the complete
  ledger. Dashboard reads status summaries only.
- Manual concurrency persists atomically with pause state. Polling respects
  unsaved edits and ignores stale responses. The existing render limiter
  resizes without losing leases held by active processes. Four applies to
  actual render slots as well as the job queue. Lowering the limit waits for
  existing renders to finish rather than terminating them.
- The portrait center-crop path crops at source resolution before scaling.
  Final resolution, frame rate, encoder preset, quality, audio and full decode
  validation are retained. Blur-background rendering keeps its existing path.

## Verification before packaging

- Full suite: **789 passed, 4 skipped, 29 subtests passed**.
- Four inline JavaScript blocks and seven external scripts passed Node syntax
  checks; both HTML templates are identical.
- Chrome UI test used the actual frontend and isolated Flask APIs with 1,264
  jobs. It checked filtering, paging, search, error details, unsaved manual
  four surviving polling, manual four surviving reload, the favicon link,
  no eager Jobs/gallery requests, and no browser page errors.
- The launcher compiled and its actual native icon method set matching large
  and small handles on a hidden isolated Windows window.
- Tests exercise preference readback, persistence failures, pause preference
  preservation and live limiter resize while a render lease is held.
- The text-encoding fixture now uses a real temporary ledger for both the
  list and detail APIs rather than mocking the previous whole-ledger reader.

## Measurements

Evidence is in checkpoints/evidence/v1.3.2/performance.json. With an isolated
1,264-job fixture containing 100 transcript entries per job, median response
time was 2,067.963 ms for the full list and 3.632 ms for a page of 25. Payload
sizes were 10,473,497 and 5,954 bytes respectively. Queue status took 0.775 ms.

With the same synthetic 1920x1080, 30 fps, six-second source and libx264
veryfast/CRF 21 settings, the portrait filter took a median 2.227 seconds
before and 1.755 seconds after, a speed ratio of 1.268. Three alternated runs
per path passed duration, frame-rate and full audio/video decode validation.
These measurements describe this machine and fixture, not every user's
hardware or the total download/transcription workload.

## Delivery checks

Build identity records the exact source commit. The installer payload check
must pass against that commit before publication: every shipped source file
must match, the new queue script must be present, versions must be 1.3.2,
checksums must agree, and mutable state or credentials must not be packaged.
The build reuses the previously verified embedded runtime with matching
requirements lock. Its tests can be skipped during packaging only after the
full offline suite above has passed.

Existing user data and older untracked recovery artifacts are preserved.
This work does not replace files inside the currently active installed app.
Users receive these changes by installing the new 1.3.2 package.
